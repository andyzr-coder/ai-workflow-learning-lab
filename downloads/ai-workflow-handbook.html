为什么需要：把复杂函数变成可实现的数据路径

通用数学库可以使用复杂范围归约和迭代。专用硬件常用 LUT（Look-up Table，查找表）与低阶多项式减少运行时工作。表越细，近似通常越好，但系数存储、译码和访存代价也变大。

像 CPU 微码表一样，查表把一部分计算成本提前到离线；类比边界是数值近似还要承担误差预算，而微码通常实现精确定义的语义。

算法与状态：四个数值对象不要混在一起

  • 数学目标 f(x)：例如理想 sin。
  • 实数近似 p(x)：拟合或插值造成第一部分误差。
  • 有限精度行为模型 p_fp(x)：系数编码、中间运算和舍入造成第二部分误差。
  • RTL 输出 p_rtl(x)：应按接口和时序与 p_fp 对齐，再检查逐位或规定容差。

FMA（Fused Multiply-Add，融合乘加）对 a×b+c 只在最终结果舍入；分开乘法与加法通常有两次舍入。数学上等价的表达式，有限精度下不一定逐位等价。XLS 浮点文档还列出具体操作的非规格化数、舍入和异常标志限制，不能只看“FP32”标签。XLS Floating-point routines，FMA 与各操作说明。

约束：误差口径与采样边界

绝对误差 e_abs=|y−f(x)|；相对误差 e_rel=|y−f(x)|/|f(x)|。f(x)=0 时后者未定义，接近零时也容易失真。可报告排除阈值后的相对误差，同时保留全域绝对误差。ULP 是相邻可表示值间距口径，需指定格式、数值区域与特殊值处理。

视频幻灯片给出 exp 的 [-20,0]、sin 的 [-π,π]、sigmoid 的 [-6,6] 各 2048 个均匀样本。它们是所测点的统计范围，不是所有 FP32 编码的穷举证明。必须额外检查段界两侧、尾端、接近零、溢出/下溢和特殊值。

完整例题：线性插值上界如何推导

交互实验刻意简化为线性插值，不复现视频的二次 FP32 电路。对 sin 在 [-π,π] 上均匀分 N 段，h=2π/N，且 |f″|≤1。插值余项满足 |f−L|≤h²/8。N=16 时，上界约 0.0192766；若输出小数位 F=10，Δ=2⁻¹⁰，最近舍入增加至多 Δ/2≈0.000488281，总上界约 0.0197649。

上界假设节点与中间插值精确、没有输出饱和。实验用 JS 双精度逼近这种教学模型，4097 点给的是采样最大误差。分段数翻倍，插值项上界变为四分之一；量化项不会自动减小，因而会逐渐成为瓶颈。节点表代理存储量为 (N+1)×B bit；不含地址逻辑，不是硬件面积。

取舍与失败：位数越多也可能更糟

为什么需要与系统位置

高层功能描述把算术意图与具体流水寄存器分开，便于探索结构。XLS 从 DSLX 经 IR（Intermediate Representation，中间表示）、优化、调度到 RTL。纯函数适合无状态计算；proc 用于带状态和通信的描述。官方概览将 XLS 明确标为实验性项目，DSLX 兼容性需按版本核对。

视频中可见版本为 v0.0.0-10782-g5ddc35c4e。本课程引用的滚动文档访问于 2026-11-08；没有将当前 API 自动视为该 commit 的行为。复现时首先固定编译器 commit 与依赖。

数据与控制路径

DSLX 源与测试 → 解释器 → 未优化 IR → 优化 IR
                                  ↓
                延迟模型 + 目标周期/级数 → 调度表
                                  ↓
                            RTL + 接口描述
                                  ↓
                     仿真回归 → 综合 → P&R → STA

每条边都可保留文件哈希与验证记录。IR 优化改变图结构，调度把操作分配到阶段，RTL 生成实现寄存器和接口。不要把 IR 当作已经完成物理放置的电路。

算法：依赖约束与资源占用

若运算 B 依赖 A，则 B 只能在 A 结果可用后执行；每级组合路径还需满足调度器的内部延迟模型。跨级存活的值需要寄存器。更多级数可能缩短每级路径，却增加寄存器、时钟树、控制和首结果等待。XLS 调度文档描述了周期、级数与寄存器成本的竞争。

交互实验采用另一种更小的“弹性流水线”：每级存一笔事务、末级 ready 决定是否出队，空位向上游传播。这个模型教握手与占用，不声称复现 XLS 的所有接口或调度算法。

定量例题：L 与 II 不同

设理想流水线延迟 L=4 cycle、启动间隔 II=1 cycle、时钟 f=200 MHz。边沿0接受首笔，边沿4输出，所以首笔延迟 L/f=20 ns；稳态吞吐 f/II=200 M笔/s。12笔在边沿0…11进入，最后一笔在边沿15完成。从首笔接受到最后完成的物理总历时（makespan）为 (12−1)×II+L=15 cycle，即75 ns；按该边界计算批次平均完成率为12/15=0.8笔/cycle。

若另选半开观察窗口 [0,16)，窗口时长是16 cycle，窗口内完成12笔，得到12/16=0.75笔/cycle。这个观察窗口包含最后完成后的1个周期；16个边沿记录本身不能推出物理历时16周期。两种有限窗口指标都不等于长期稳态1/II=1笔/cycle，报告必须写明起止边界。

增加到8级而 II仍为1，首结果变为40 ns，稳态仍为200 M笔/s。提高时钟能否抵消延迟，要重新检查实际路径、寄存器开销和约束，不能单凭级数判断。

约束与反例

背压会拉长事务延迟并降低窗口吞吐；输入到达率大于服务率时，入口队列会增长。有限缓冲必须定义阻塞或丢弃策略。一个生产者在 valid=1、ready=0 时擅自改变 data，会破坏事务保持，而不是“仅仅慢一点”。

调度时钟是目标或内部模型约束；最终 STA（Static Timing Analysis，静态时序分析）还取决于标准单元、连线、布局、时钟不确定性与角点。内部模型可行不保证布线后时序通过。

  • 画出刺激、DUT、独立参考和记分板的数据路径
  • 设计能击穿错误实现的边界测试
  • 用机器可读证据约束 AI 修复并设置退出条件

为什么需要：生成器与检查器不能共同猜答案

把 DUT（Device Under Test，被测设计）想成 CPU 数据通路，记分板想成独立执行参考 ISA 的对照机。编译器只能排除某些语法和类型问题；它不知道你要的是饱和还是回绕。两份代码来自同一段错误解释，即使逐位相同，也只能说明共同犯错。

录屏中对 Python、DSLX 和 RTL 的阶段性对照，是值得保留的工程骨架。但数学逼近是否够精确、两种实现是否一致，是两个不同问题；把同一个错算法搬到每一层，仍可能全部一致。

系统位置与数据路径

冻结规格 → 测试输入 → DUT → 实际输出 ─┐
       └→ 独立整数参考 → 期望输出 ───┤ compare → PASS/FAIL
工具版本、随机种子、输入哈希、日志 ───┘
FAIL → 分类与最小反例 → AI 提交局部修复 → 全部回归
  • 冻结验收条件：输入 a,b 为 0…255，输出 min(255,a+b)，复位清除 valid，背压时保持数据。
  • 只读参考模型和回归用例；AI 改它们需要单独解释规格变更，不能为了过测试降低预期。
  • 错误类别先分：环境/编译、数值、握手、复位、未知态、超时。每类对应不同修复动作。

状态变化：一个弹性输出寄存器

接口使用 valid/ready（有效/就绪）握手：只有同一时钟边沿两者都为 1，事务才发生。单级模块令 in_ready = !out_valid || out_ready。若输出寄存器空，或者旧输出即将被消费，就能接收新输入。否则保持 out_valid 与 data，禁止新输入覆盖旧结果。

在同步电路中，“某条信号出现上升沿”与“所有下游非阻塞赋值完成”不是同一观察时刻。cocotb 2.0.0 的时序文档区分边沿事件和 ReadOnly 稳定采样阶段；实际测试还需核对仿真器语义。

来源：cocotb Timing Model，Values Change / End of Time Step。本仓库实测采用 SystemVerilog testbench，避免把未运行的 cocotb 示例说成已验证。

约束与验收阶梯

  • lint：位宽、隐式网线、风格与可疑结构；不是完整功能证明。
  • 仿真：只对运行的输入和序列提供证据。固定随机种子是复现条件，不是覆盖充分性的证明。
  • 形式化：在明确假设、状态范围和属性下证明；过强假设可能排除真正缺陷。
  • 综合 / STA：检查映射后的实现与时序约束；功能仿真 PASS 不等于时序收敛。
  • 系统性能：微模块的吞吐与整机延迟不相等，还要纳入调度、内存和资源冲突。

完整例题：4 个普通输入为什么漏掉溢出

规格 y=min(255,a+b)。错误实现 y=(a+b) mod 256。对 (1,2)、(10,20)、(40,60)、(0,0) 两者都相等，4/4 PASS。加入 (255,1) 后，期望 255，实际 0；加入 (128,128) 后，期望 255，实际 0。反例直接指向截断前没有检测第 9 位进位。

y = 255 if sum9 > 255 else sum9

assert compare_only_on(valid && ready)

取舍：快反馈与独立性

快速 lint/单元用例放前面，昂贵回归和物理实现放后面，可以减少无效等待。局部修复也必须跑相关全回归，否则可能修复溢出却破坏停顿。固定预算，例如最多 3 次修复、每次 10 分钟、失败保留最小反例，是教学配置而非最佳实践数字。

AI 可解释日志、提出反例和补充测试，但最终接受条件由确定性工具与审查约束。OpenAI 的修复闭环示例也强调可执行反馈；将其迁移为 RTL 闭环是本课程的工程设计。官方示例。

失败与误解：把错误复制成 golden

如果参考模型也使用 (a+b)&255，那么 (255,1) 的“期望”也变成 0，测试仍 PASS。实验室允许切换这个错误参考，观察 PASS 与真实符合规格的差异。修复办法不是再问一个模型投票，而是用明确规格推导参考式、保留反例、审查两个实现的共同来源。

不要把局部仿真的通过率命名为流片成功率。也不要让 agent 修改测试数据直到变绿，而不留下规格变更记录。

定量模型与单位

令O为总运算量(op)，P_cap为同一统计范围内不能超过的计算速率(op/s)，Q为某存储层级的访问字节(byte)，B_cap为该层级不能超过的带宽(byte/s)。则T_c,min=O/P_cap、T_m,min=Q/B_cap，运行时间必不小于max(T_c,min,T_m,min)。这只是必要下界；依赖、启动与竞争可能使实际时间更长。运算强度I=O/Q(op/byte)，相应性能上界为min(P_cap,I×B_cap)。Roofline原始论文提供这一界限与瓶颈分析思路。

若用B_model=η×B_peak表示假设的持续有效带宽，T_m,est=Q/B_model就是该效率假设下的传输估算，不能自动成为真实硬件的严格下界。一次微基准测得的平均带宽也不是所有负载的硬上限。采用测得的可持续带宽构建经验屋顶线时，应说明测试负载与适用范围。

在本章简单模型中，固定服务速率后，完全重叠估计T_est=max(T_c,est,T_m,est)+T_launch；完全串行估计T_est=T_c,est+T_m,est+T_launch。这两个等式依赖各自的排程假设。只有同一统计范围的O、Q、P、B才能放进一个式子：整层O不能配单tile的Q；MAC计几op、GB还是GiB、每核还是全芯片，都应写在报告上。

完整例题：翻倍算力为什么没加速

原创教学负载：O=512 Gop、Q=64 GB，计算模型假设以128 Gop/s持续服务；外部带宽峰值B_peak=32 GB/s，假设效率η=0.5，故B_model=16 GB/s。计算估计T_c=4 s，传输估计T_m=4 s。完全重叠并加5 ms启动得到4.005 s；完全串行得到8.005 s。这是所选效率与排程假设下的模型结果，不是硬件严格下界或实测。若仅用不能超过的32 GB/s峰值，能推出的传输下界是2 s。

把计算模型速率提高到256 Gop/s，只把T_c降到2 s，重叠模型总时长仍为4.005 s。再把Q减半到32 GB，T_m也变为2 s，结合后总时长为2.005 s。单项优化可能被另一资源遮住；应分别改变参数观察瓶颈迁移，并记住持续计算速率本身也是模型假设。

从静态式子到事件状态

对非流水、非抢占的独占资源，事件开始时间=max(所有依赖的数据就绪时刻，资源可用时刻)，结束时间=开始时间+服务时间；结束后释放该资源。多资源事件还必须同时获得所需资源。多个独立事件可以重叠，但共享端口需要排队或明确的带宽分享规则。

对流水资源，结果延迟L与再次发射间隔II必须分开：next_issue=start+II，result_ready=start+L。依赖者等result_ready，独立的新事务则可在next_issue发射，还要满足内部容量、端口和背压条件。例如L=4、II=1的理想单元可每拍接收一笔；若错误地直到结果完成才释放发射机会，就会把II错建成4。不能用一个“busy至完成”的状态表示所有流水资源。

资源模型可分固定服务与随shape变化的成本。TopK等操作还可能依赖算法和数据分布；服务、排队等待、发射限制及结果就绪应分别记录，不能用一个与shape无关的“每元素周期”解释所有情况。

取舍与反例

解析模型的快来自省略细节。它适合上下界和灵敏度，不适合凭空预测bank地址冲突。周期模型若配置过时、端口共享关系错误，也可能更慢但不更准。增加细节前应说明它能改变哪个设计决策，并准备校准数据。

反例：4个并行请求访问同一单端口bank。总容量足够、总字节很少，Roofline仍可能乐观；地址映射与仲裁决定串行服务。另一个反例是启动开销主导的小算子，总op很少也不代表时间可忽略。

算子融合与 L1：数据搬运为什么支配结果

录屏在模型图、指令拆分和L1配置之间反复往返。这里的主线是：先保留算子语义，再决定数据怎么切、放在哪里、何时复用；融合收益来自减少搬运，但可能被容量或端口代价抵消。

能力目标

  • 从张量shape与dtype计算存储量
  • 计算中间结果写回/重读的流量
  • 分析融合的容量、活跃区间与端口代价
  • 比较独立算子与融合实现时保持同一计量边界

为什么需要与系统位置

一个计算图有很多看起来简单的算子。逐个运行时，中间张量可能写入外部内存，再由下一算子读回。融合把这些中间量留在寄存器或本地buffer，减少往返。和CPU编译器融合循环的直觉相似，但加速器还受tile尺寸、专用引擎、片上存储和DMA约束。

对象与数据路径

未融合：读X → 算子A → 写Y → 读Y → 算子B → 写Z
融合：  读X → [A → 本地Y → B] → 写Z
映射约束：tile shape、dtype、生命周期、buffer、读写端口

图的节点表示语义，不一定是一条ISA指令；mapping描述如何用硬件资源实现。把一个复杂算子拆成基础运算可以揭露SFU或归约成本，但过早拆细也会让分析冗长、重复计算搬运。应保留语义层与实现层之间的映射。

MLIR Transform官方教程的结构化操作与Loop Fusion部分提供了保留索引/迭代语义并表达融合的具体例子。这里的容量、端口和外部流量算例是课程增加的工程分析；IR合法转换本身不证明目标硬件加速。

算法：容量靠活跃区间计算

工作集不是把所有张量容量简单相加，也不是只看最大一个张量。应在执行时间线上计算同时活跃的输入、输出、累加器和临时buffer。双缓冲可能把某些输入/输出buffer占用加倍；对齐、padding和元数据也需要空间。

如果buffer复用是推测而未实现，就不能在模型中提前“免费释放”。每次写入、读出和释放都应关联事件或明确的静态生命周期。容量通过后还要核对同拍端口需求与bank映射。

完整例题：融合省了多少搬运

原创教学张量Y有1,048,576个BF16元素，每个2 byte，所以容量为2,097,152 byte=2 MiB。未融合的一次写Y和一次读Y共4 MiB。假设持续有效外部带宽为16 GB/s，忽略启动与其他开销，传输时间估计为4×2²⁰/(16×10⁹)=0.262144 ms；只有把16 GB/s明确作为不可超过的带宽上限时，这个值才是相应下界。融合可消去这部分外部流量，却不保证端到端恰好快0.262144 ms，因为传输可能原已与计算重叠。

设本地容量4 MiB，X、Y、Z各2 MiB，朴素同时保留共6 MiB，不可行。若按半张量tile切分，并证明Y可消费后立即释放，就可能降低峰值活跃量；若还要双缓冲输入，必须重新计算，不能默认依旧放得下。

约束：精度、归约与数据相关操作

重排浮点归约顺序可能改变舍入；softmax等归约有跨元素依赖，不能像逐元素激活一样任意独立切块。融合的语义验证要检查边界、shape、mask和特殊值。TopK或稀疏路由还可能改变访问局部性和负载均衡。

把所有操作都折算成MAC吞吐，会漏掉Exp、除法、归约、scatter/gather等不同资源。相同op计数并不意味着同一服务速率。

取舍与失败案例

融合收益：减少中间写回、减少启动次数、改善复用。成本：工作集增加、实现复杂、并行机会减少、寄存器或L1压力、调试和验证边界扩大。强行融合可能引发spill到外存，反而比未融合更慢。

反例：两个并行分支共享Y。把Y仅保留在某一融合组内部，却忘记另一个消费者，会漏掉必要搬运或重复计算。正确方法是对图的所有消费者和生命周期做检查。

让 AI 帮你编写 RTL、算子模型或仿真器，关键不在于对话轮数，而在于每次改变都留下可复查的输入、工具结果与判断依据。本章把 agent 当作工程控制系统来设计。

横向关联：架构模型：先界定问题，再选择抽象层级 · 算子融合与 L1：数据搬运为什么支配结果 · PPA 与候选筛选：证据、约束和 Pareto · 选择 AI 芯片工程 Flow：按任务、证据与成本比较

能力目标

  • 画出规格、候选实现、工具执行与独立判定之间的数据和控制路径。
  • 定义可复现的工具契约，区分失败、成功与结果未知。
  • 建立独立的 golden reference，识别实现和测试共享错误的风险。
  • 计算串行/并行检查的墙钟时间，并说明资源和依赖假设。
  • 设计有版本、预算、职责和集成门槛的协作流程。

为什么需要：生成完成不等于工程完成

一个输出数值的性能模型可能把带宽单位误写成 byte/s；一个能编译的加法器可能回绕而规格要求饱和；一个通过的回归可能运行了旧提交。它们共同的问题是：产物与规格之间缺少明确的证据链。

工作流（workflow）预先确定工具和分支；智能体（agent）让模型在约束内选择下一步。确定的编译、报告解析和测试适合固定节点；故障定位、候选修复适合由模型提出方案。这个划分来自 Anthropic 的工程模式总结，属于实践建议，不是芯片性能基准。

可以把流程类比为 CPU 的控制状态机：规格和任务状态是控制寄存器，工具是执行单元，日志是可观测信号。类比的边界是：模型决策具有随机性，外部工具也可能超时或产生部分输出，因此不能把语言回答视为稳定的组合逻辑。

系统位置：谁提出改变，谁决定通过

完整路径为：人确认规格 → 版本化契约 → AI 提出候选 → 工具适配层执行 → 独立检查器判定 → 证据归档 → 接受或修复。模型读取日志并选择下一步，但不能把自己的“已完成”覆盖检查器的失败状态。

至少分开三类对象：①规格与约束，例如输入形状、精度、复位、吞吐口径；②候选实现，例如 RTL、模型代码、映射参数；③证据，例如测试用例、事件轨迹、原始计数器、工具报告。修改规格应产生单独差异和理由，不能为了通过测试悄悄改预期答案。

工具返回值除了 exit code，还应含 run_id、输入哈希、工具版本、完整命令、开始/结束时间、报告路径和完成状态。零退出码只表示工具按其约定结束；空测试集合、缺失报告、旧缓存仍须识别。

上下文不是全量粘贴：建立最小可复现输入

一次修复任务的上下文按优先级排列：规格版本和不可改变项 → 当前提交与可写范围 → 验收命令 → 最小失败输入 → 期望/实际差异 → 相关实现片段 → 已排除的假设。完整日志存文件，提示只放相关窗口与可追溯路径。

工件必须回答的问题
spec.json位宽、单位、边界、吞吐/延迟定义是什么？哪些来自规范，哪些是估算？
candidate.patch基于哪个提交？改了什么？是否越过职责边界？
run.json运行哪套工具与配置？是否使用旧缓存？哪些步骤完成？

架构模型尤其要记录参数出处：公开规范、微基准拟合、设计假设、占位值应分别标记。未知值保持未知，再做敏感性区间；AI 补出的一个“合理常数”不能升级为硬件事实。

状态变化：有上限的反馈环

建议显式记录状态：SPEC_READY → PLAN_READY → RUNNING → EVIDENCE_READY → ACCEPTED。已确认失败进入 REPAIR_PROPOSED，再运行；预算耗尽、规范矛盾或缺失关键资料进入 NEEDS_REVIEW。任务完成的条件是证据满足契约，不是对话结束。

先分类再修复：环境错误应修依赖；语法/类型错误应修接口；功能错误应定位语义；模型偏差应拆解计数与资源占用；PPA 不达标应审视结构和约束；结果未知则先查询执行状态。不同类别不能都用“再让模型重写一次”处理。

AutoChip 2025 v3研究了编译/仿真反馈驱动的有限轮次 RTL 修复，但收益随所测模型和预算变化。它使用 VerilogEval V1，不能把结果直接套到 V2 或当前模型。教学流程借鉴其反馈结构，不承诺复现其收益。

约束：持久化、重试与幂等

检查点（checkpoint）保存流程状态；幂等（idempotency）指重复请求不会产生额外业务效果。二者不同。若提交 P&R 作业成功但回执丢失，直接重试可能重复占用资源，不能把超时当成“没有执行”。LangGraph 故障恢复文档明确提醒：节点重试会重新执行，外部副作用没有天然的 exactly-once 保证。

做法是为同一次逻辑操作使用稳定 operation_id：先查询集群作业和产物，再选择接管已有执行或重新提交。每个 trial 使用独立目录；报告写临时文件，完整性校验后才标记完成；验收时核对输入哈希。耗时长的执行宜与结果解析拆开，使解析重试不必重新跑 EDA。

并发写同一个结果文件、旧分支覆盖新实现、重试重复提交，都是流程正确性问题，即使模型每次回答都正确也会发生。

独立判定：先确定答案从哪里来

参考判定器（oracle）可以是数学定义、独立实现、性质约束或经过校准的测量。它不必由另一个大模型担任。若生成器和测试器都误解同一句规格，两者一致也可能一起错。

RTL 例：8 位无符号饱和加法要求 min(a+b,255)。对 200+100，正确输出255，8位截断输出44。独立数学参考和边界用例能揭示错误；从错误 RTL 自动抄出的期望值不能。cocotb 负责连接 Python 与 HDL 仿真器，正确性仍来自你的参考与检查。边沿后立即读数还可能产生采样竞争：cocotb 2.0.0 timing model区分 RisingEdge 事件与当前时间步稳定后的 ReadOnly。

架构模型例：先以手算验证单资源无冲突场景，再加共享端口、队列、依赖和背压。检查守恒：发出请求数=完成数+在途数；资源使用不超过容量；任务不能早于输入就绪。随后以独立微基准校准延迟和吞吐，留出未参与拟合的形状验证。Accel-Sim 作者框架展示了 trace、模型与硬件关联比较的工程分工；其模型和验证结果不自动适用于新芯片。

完整算例：并行节省了什么

以下均为教学假设，不是实测。一次候选生成8 s，编译4 s；编译后仿真24 s、性质检查36 s；汇总3 s。两项检查互不依赖、有独立机器和许可证、无排队、均成功。

串行墙钟时间 T_serial=8+4+24+36+3=75 s。并行时间 T_parallel=8+4+max(24,36)+3=51 s。加速比=75/51≈1.47。检查资源消耗仍为24+36=60资源秒；墙钟减少不表示总计算量或费用同比减少。

若失败后定位和修复需10 s，并只重跑上述编译与两项检查，则追加10+4+36+3=53 s，总计104 s。若仅有一份共享许可证，24和36不能重叠，51 s 的结论不成立。若存在缓存、失败概率、资源抢占，应另建模型，不能沿用这个理想公式。

别混淆四个时间：工程工具运行的秒、硬件模拟周期、候选硬件的工作频率、用户请求的端到端延迟。一个模拟器运行更快，未必意味着它模拟的芯片更快。

取舍与误解：何时增加 agent

先让一个受约束的流程稳定工作，再考虑并行。适合拆开的任务包括：同一冻结规格的独立测试设计、互不重叠的模块实现、不同参数 trial。每个工作者需要基准提交、可写文件、接口、产物格式和预算；集成者在合并后的提交上重新验证。

两个 agent 同时改同一文件会增加冲突；多个 agent 共享错误前提不会形成独立证据；让评审者只能读实现而不读规格，会偏向确认现有代码。多 agent 的价值来自任务结构和检查独立性。

VerilogEval 作者仓库说明版本、提示与采样设置的变化，因此“成功率提高”必须同时说明任务集和尝试预算。阅读完成只记学习进度；能独立画出状态图、复现一次失败并证明修复，才记能力证据。下一章用相同原则选择具体工程 Flow。

选择 AI 芯片工程 Flow：按任务、证据与成本比较

当前值得借鉴的是能把工程输入、工具反馈、独立验证和版本追溯连接起来的流程。本章围绕架构性能建模，再比较 SFU/HLS、RTL 修复、规格生成、知识检索与 PPA 探索；工具能力与研究证据分开评价。

先修：工程 Agent：状态、上下文与可验证交付 · PPA 与候选筛选：证据、约束和 Pareto

横向关联：架构模型：先界定问题，再选择抽象层级 · 算子融合与 L1：数据搬运为什么支配结果 · 验证闭环：怎样证明 AI 写的实现符合规格

能力目标

  • 按任务输入、交付物、判定器和失败方式选择工程 Flow。
  • 区分确定性工具自动化、LLM 候选生成与代理编排。
  • 建立架构模型的手算、微基准、校准集和保留集验证链。
  • 在相同精度、负载、资源和尝试预算下设计 PoC。
  • 先检查功能与硬约束，再比较性能、能量和人工成本。

先定义好在哪里：不是一张工具排行榜

“做得好”在本课程中表示：任务边界明确、输入输出可检查、错误能退出、证据可重放，并在相同预算下有实用价值。一个擅长生成 RTL 的工具不能直接与知识库问答平台比较；旧论文结果也不能替代当前版本的自有任务验证。

为每个候选方案填四项：输入契约是什么；交付物是什么；谁独立判断正确；最可能在哪种边界失败。再量化正确率、首次正确耗时、尾部耗时、总 token/计算资源和人工介入。先建立最小基线，再加模型或多 agent，才知道收益来自哪里。

证据标签：工具文档说明能力；作者论文说明特定实验；厂商网站说明产品主张；本章流程是工程设计建议；本章数字均为教学算例，不是这些工具的测量值。

系统位置：让不同工具承担不同职责

问题建议组合与交付独立证据
架构性能预测规格 schema → AI 辅助解析/事件模型 → 轨迹与指标手算、不变量、微基准、未拟合负载
算子映射与融合结构化图/IR → 合法候选 → 容量/资源模型数值等价、实际移动量、时间线
算法数据路径golden → DSLX/XLS → RTL → EDA误差预算、RTL回归、同条件STA/PPA
局部 RTL 修复冻结规格 → 候选 patch → lint/仿真反馈独立测试与性质、全量回归
寄存器/文档原表 → 规范化 schema → 确定性生成源单元格追溯、行为语义检查
工程知识问答版本过滤 → 检索 → 引文与假设 → 复现引文支持结论、实际工具验证

这些是可组合的工程角色。自动化编译器、仿真器和搜索器不因为被 AI 调用就变成 AI 模型；模型解释报告也不改变报告本身的证据等级。

首要 Flow：让 AI 帮你建立可校准的架构模型

先以显式 schema 固定算子、精度、形状、存储层次、带宽单位、资源速率和依赖；再让 AI 实现解析估算与事件模型。架构初期可用分析模型快速扫描；怀疑端口争用、队列、背压或启动开销时，再增加相应事件。更细不是自动更准确，每新增状态都需要验证。

Timeloop/Accelergy把工作负载、映射、架构与技术成本分开；v4 架构格式显式描述存储容量、位宽、读写/共享带宽和缓冲份数。它适合借鉴输入结构与映射分析，但不能假定任意自定义指令、银行冲突或融合执行都已被覆盖。MAESTRO也是数据流/成本建模考察对象，选用前要核对支持算子与硬件假设。

验证顺序：①无冲突单操作手算；②依赖链与共享资源反例；③请求守恒和资源容量不变量；④小型独立微基准测参数；⑤冻结参数后用保留形状验证误差。用平均误差掩盖特定算子失真不可接受，应按算子、规模、访存模式分层报告。

模型输出应带证据等级和假设：这是估算，不是实测；遗漏了哪些资源；参数来自何处；对关键未知参数的敏感性有多大。AI 可以帮助补代码和分析残差，不能靠修改每个样本的常数“拟合正确”。

融合与映射：先保留语义，再比较资源

用中间表示（intermediate representation, IR）记录形状、索引、归约和依赖，能把“图上连在一起”变成可检查的计算结构。MLIR Transform 官方教程展示了结构化操作与融合的表达方式，某些融合可去掉临时缓冲。编译合法性与硬件收益仍是两个问题。

每个候选同时检查：计算结果/舍入是否符合要求；tile 的活跃工作集能否放下；双缓冲是否真的有两份容量；读写端口是否互相争用；融合是否增加重算或降低并行度。算子名相同不代表 ISA 分解相同，分解到不同执行资源后必须重新计算工作量和传输量。

教学反例：融合少写一个中间张量，但使每个 tile 的活跃数据超过本地容量；若发生 spill 或缩小 tile 导致更多重复读取，总时间可能增加。先画两条时间线，再比较总流量和关键资源，不能只统计少了几次 kernel launch。

HLS 与规格生成：把确认过的含义交给确定性工具

SFU 等有明确数学定义的数据路径，可采用独立高精度参考 → 误差与位宽预算 → AI 辅助 DSLX → XLS 测试/IR/调度/RTL → RTL回归 → 同工艺实现。XLS 官方说明将其定位为仍在演进的 HLS 工具链；调度文档中的内部延迟模型不是布线后 STA。任意 Python 并不能不经转换就成为可综合硬件。

Excel 规格到代码宜先提取规范化字段和源单元格地址，歧义交给规格责任人。对于控制/状态寄存器，PeakRDL可从统一描述生成多种产物，避免多份手工同步；同时核对已知限制。AI 适合解释和发现歧义，确定性生成器适合重复产出。

反例：W1C（写1清零）被解析成普通 RW（读写），RTL、头文件和文档可能完全一致却全部错误。除结构一致性外，必须独立验证访问语义、复位值、保留位和跨时钟更新等实际行为。

RTL 修复与知识检索：反馈必须能反驳候选

局部 RTL 修复的基线是一轮候选加人工检查；增强方案是有限预算的 lint/编译 → 自检仿真 → 最小失败日志 → patch → 全回归。AutoChip 2025提供这种 EDA 反馈结构的研究案例；与 VerilogEval V2比较时须注意它使用的是 V1。测试通过不等于覆盖全部功能，不能把公开题答案泄漏当作泛化能力。

ChipNeMo研究工程问答、EDA 脚本与 bug 总结，使用领域数据和检索；内部语料限制外部复现，旧模型比较不代表当前排名。Dify 检索节点提供元数据过滤、重排与上下文引用等组装部件。应用时按项目、文档版本、工具版本过滤，再要求回答区分原文事实和待验证假设。

“有引用”不等于引用支持结论；一个型号的手册也不能填补另一个型号的未知参数。知识流的终点应是最小复现或可追溯决策，而不是听起来可信的答案。

PPA 和商业平台：统一任务条件后再做选择

OpenROAD Flow Scripts连接 RTL 到物理实现阶段；AutoTuner提供配置搜索与指标采集。AI 可以提议候选或解释失败，但不能替工具编造 timing、面积或功耗。先固定功能、PDK/库、PVT、时钟/IO约束、面积统计范围、流程阶段和预算，再筛除不可行点，最后比较 Pareto 前沿。

放宽时钟获得更小面积改变了问题。用默认活动率估计的动态功耗不能直接当成目标工作负载实测功耗；没有 VCD/SAIF 或其他活动依据时须明确其假设。生成 GDS 也不等于通过目标代工厂全部签核。

ChipAgents可作为商业集成平台的 PoC 候选；公开产品页面属于厂商能力主张，本课程没有验证其兼容性、部署、报价或加速倍数。n8n evaluation这类编排工具可用于派发、评测与报告，但执行成功不能替代 RTL 正确或模型校准。选择依据应是自有脱敏任务的可复现证据。

完整算例：统一预算的比较怎么报告

以下为教学数据，不指代任何工具。两条流程各运行同一20个独立任务，时限120 min、相同工具与输入，统计全部失败和重试。A成功14个，消耗80,000 token；B成功16个，消耗120,000 token。

成功率 A=14/20=70%，B=16/20=80%。绝对提高10个百分点；相对提高(80%-70%)/70%≈14.3%。每个成功任务分摊的总 token 为 A≈5,714，B=7,500；分子必须包含失败尝试，不能只数成功那一轮。

B在这个样本中多完成两个任务，也消耗更多 token。未给输入/输出 token 划分和当时价格，不能算费用；token 也不是能耗。20个样本不足以仅凭这两个百分比证明普遍优势，还要保留逐任务配对结果、重复运行、人工介入时间和失败类型。

架构模型的比较另加：同精度/形状/融合方案的预测误差、资源计数残差、保留集表现；实现性能的比较另加：同约束的时序和能量。把不同层次的数字塞进一个“综合提升倍数”会失去可解释性。

实施计划与迁移：从一个可证明的小闭环开始

三天路线：第1天冻结一个算子或小模块，写手算和独立参考；第2天搭建有版本日志的生成/执行/反馈闭环；第3天加入反例、未知状态恢复和同预算比较。完成标准是一条可复现证据链，而不是工具列表。

两周路线：第1–2天契约与基线；第3–4天模型或 RTL 的最小实现；第5–7天边界、资源冲突和保留集；第8–10天扩展融合、XLS或PPA中的一个方向；第11–12天注入过期报告、丢回执、错误单位等故障；第13–14天统一预算比较、复查来源与复现说明。

用熟悉的 CPU/GPU 知识迁移：把新执行单元视为资源，把依赖视为发射条件，把本地存储视为受容量和端口约束的资源。但不要直接移植缓存一致性、warp 调度或乱序执行假设；只有目标架构明确存在的机制才能进入模型。未知参数先列为假设和敏感性范围。
